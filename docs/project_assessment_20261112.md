## 1. 当前数学问题与实现口径

设原始 OD 数为 R。任务集合包含 R 个单订单任务；K2 额外包含 R² 个有序双订单任务，包括同 OD 双单。稳定 ID 保留全部任务，零率任务的指派固定为零。任务率 ν[q] 在网络设计之前由固定路径成本、支持和剩余需求重构，不依赖优化过程中的基地开闭决策。

每个任务独立选择出发基地：

\[
\sum_l\alpha_{ql}\le 1,\qquad
\sum_{p\in\mathcal P_{ql}}f_p=\nu_q\alpha_{ql}\rho_l.
\]

同首单的不同任务可分配到不同基地；返回基地由路径决定。路径仍保留返回基地、空载调位、无人机平衡、柜点占用和骑手送到家的时限。双任务按订单出现次数消耗需求，AA 计两次。不能把旧的首单绑定指派或基地对指派结果作为当前任务模型的结果。

固定广义任务重构是规划层的均值近似。剩余需求 Poisson 计算没有证明重构后任务流是某个在线匹配策略产生的独立 Poisson 过程；本轮正确性检查针对这套已经选定的数学模型及其实现，不改变该建模假设。

生产求解器为 C++/CPLEX：整数设计 master 加连续 SOCP recourse，使用完整物理域定价产生认证。Python 的物理重算是独立校验工具；保留的 Python/Gurobi 优化器是历史模型，不是当前固定任务模型的直接对照。

## 2. 正确性评估与已修复问题

| 问题 | 影响 | 本轮处理与证据 |
|---|---|---|
| 输出路径子集被用于重构固定任务率 | 删掉双任务路径并同时伪造任务率，可能通过原独立校验，即校验了不同的问题 | 从输入完整物理域流式重建最低任务成本和出发支持，再检查保存任务率。删除双任务并伪造率的回归现在拒绝；合法 compact 输出仍通过 |
| 零率任务允许非法指派通过校验 | 流量等式乘以零后看不出 α 非零，但原生模型将其固定为零 | 使用独立参考率的精确零掩码检查 α；单任务、双任务和极小正率均有回归 |
| Python 预检比原生输入宽松 | 浮点形式的维度、重复日期、越界时间窗可能预检通过但启动失败 | 对齐整数标量、默认 K、日期及 0–24 小时时间窗，保留合法 CSV/1 兼容 |
| 长累加仅使用固定末尾裕量 | 当 long double 精度等于 double 时，固定裕量不能覆盖任意任务数的逐项舍入 | 两个定价后端共用非负乘积及累加逐项向上舍入；保留原最终保护和非有限拒绝 |
| Windows 被当作 Linux 构建 | 库目录、库名、链接参数、时间函数及哈希后端不适用 | CMake 区分 MSVC/x64，匹配 CPLEX 版本库与运行库；Windows 使用 BCrypt、gmtime_s 和文件替换接口 |
| 运行器接受零时限而原生拒绝 | 包装层参数契约不一致 | 新运行器要求正时限；零、负数、NaN、Inf 均在启动前拒绝 |
| 历史文档仍被标作当前模型 | 容易据错误的 α[r,l] 而不是 α[q,l] 设计实验 | 统一当前入口，给旧模型文档标明历史口径，保留原数学正文 |

完整域校验使用和普通 Python 枚举相同的路径生成器，避免新增第二套物理枚举逻辑。收集器保持既有 ID、顺序和停止语义；流式统计不保存所有已完成服务路径。只有正常遍历结束才提供完整统计，中断会抛出异常，不将部分扫描标为通过。当前服务器运行器为独立校验另设默认 300 秒外部上限，可显式调整；直接调用 `build_operations` 仍没有内部扫描时限。非 direct 历史路线模式仍可能缓存腿路线。

数值探针构造 1,640 个任务：一个大率、1,636 个极小正率及三个零率。精确参考修正为 1.0000000000000908，模拟原 binary64 固定末尾裕量得到 1.000000000000057，新双后端认证修正不低于参考。本例揭示局部累加保护的不足，**没有声称旧版本实际已经给出了错误的全局 LB**：外层还存在其他保护量。修复消除了该局部组件对更高中间精度的依赖；整个求解器仍需 Windows 数值验收。

### 证书与状态复核

当前遗漏服务列修正遵循独立任务语义：

\[
\Delta_{\rm service}=\sum_q\nu_q\max_l
\left[-\min\{0,\bar c_{ql}^{\min}\}\right].
\]

它先对每个任务取基地最大值，再按任务求和。不能把同首单任务先合计再取最大，后者对应另一种绑定指派模型。完整目录扫描和标签后端均已按当前语义实现；未完成完整域检查不能宣称新的定价证书。

复核还覆盖：

- 任意 L 的双任务联合 LP 只生成系数，完整 `(L+1)²` 状态表检查与保守修正后才能发割；该 LP 的目标或 best bound 不进入原问题 LB。
- 设计面证书采用任务的 L+1 个状态，并保留其他设计自由；不同任务的总成本下界不相加。
- 设计缓存未闭合区间继续求解，缓存割重复时回退；保存发生在 incumbent cleanup 之前，局部下界不直接作为全局 LB。
- 稳定化主问题、受限列修复和 CG→ALNS 信息仅服务候选选择；候选经过原模型核验，试探下界隔离。

这些分支的静态检查和所列小型探针未发现新的确定缺陷；这不是对全部实例、数值条件或未来配置的形式化无错证明。

## 3. 必要精简及保留边界

**联合割候选选择。** 原实现收集并排序所有合格任务对，最后只处理前八对。K2 的任务数 Q=R+R²，使任务对数量达到 O(Q²)。本轮改为保留至多八项的堆，严格复现原稳定排序的同分顺序；空间由 O(Q²) 降为 O(8)，候选排序工作由 O(Q² log Q) 降为 O(Q² log 8)。任务对枚举本身仍为 O(Q²)，没有改动状态表或割公式。L2/L3 穷举参考顺序与新结果一致，超时明确标记选择未完成。

**路径与验证职责。** 一个路径生成器同时支持完整收集与流式统计，精简重复遍历实现；原模型点核验继续独立于求解器矩阵。

**依赖与运行入口。** C++ 求解不需要 Python；Python 独立校验不需要 Gurobi。`gurobipy` 移入可选 `.[gurobi]`，历史求解器按需导入。Windows 当前流程收拢为打包、验收、单例运行三个脚本；不依赖历史 POSIX 进程组与 `wait4` 调度器。

**交付内容。** 白名单源码包只包含需要的源码、验证、构建说明、配置和冻结派生算例，不复制旧结果、机器二进制、许可证、Git 或原始订单。仓库中的历史脚本与模型没有删除，既有冻结实验也没有改写。源码行数不是精简目标；重点是服务器只需理解一个当前模型和一条可审计运行流程。

`benders.cpp` 仍承担较多状态机职责，历史实验模块数量也较多。此阶段不进行大范围重排，因为它会同时改变生命周期、预算与证书恢复。后续可先把不可变模型域、recourse 状态与证书记录提为内部职责，并以现有测试保护，保留小的外部接口。

## 5. Windows 交付状态

安装、PowerShell 命令、CPLEX/JSON/编译器核对、完整验收和串行比较见 [Windows 运行手册](server_runbook_20261112.md)。用户目前尚不确定服务器是否安装 CPLEX/MSVC，因此不预设具体安装路径或许可证已可用。

Windows 原生支持按 MSVC x64 与实际 CPLEX 库布局配置，浮点选项采用 `/fp:strict`，并使用系统哈希与文件替换接口。该选项的特殊值和收缩语义依据 [Microsoft 文档](https://learn.microsoft.com/en-us/cpp/build/reference/fp-specify-floating-point-behavior)，运行库选择依据 [CMake 文档](https://cmake.org/cmake/help/latest/prop_tgt/MSVC_RUNTIME_LIBRARY.html)。它们提供构建依据，不替代目标机器的数值检查。

交付包没有包含第三方求解器或许可。Windows 应自行构建 `.exe`，记录 CPLEX、MSVC、JSON、Windows 和 Python 依赖版本，使用新目录保存验收。通过后再冻结服务器源码包清单、实际二进制 SHA-256 和输入 SHA-256。当前只完成本地准备与封装，不声称已经上传或部署。

## 6. 后续数值实验与算法方向

### 第一优先级：固定可复现的服务器基线

先跑安装探针与 `check_server.py`，再用最小的实际研究算例检查完整日志、峰值内存和预算退出。确认有效的最终解与独立校验均可保存后，冻结环境和源码。初期串行、单线程，避免把并发负载误读为算法差异。

正式比较使用同一任务模型、原始市场、物理输入、seed、线程、时间预算和停止精度，比较完整 CPLEX 与 `performance-20261105`。失败、内存不足、验证超时和无有效 incumbent 都保留独立状态；最终解、恢复 checkpoint 和追加恢复耗时分开。不同日期 preset 不是不同历史模型的身份凭据。

### 第二优先级：先测机制，再增加策略

| 成对消融 | 主要诊断 | 可以回答的问题 |
|---|---|---|
| 标签 / 完整目录联合定价 | 每轮定价时间、CG 轮数、首次完整证书时间 | 扫描减少的开销是否抵消了剪枝机会与新增列负担 |
| 同设计延续 / 跨设计 RHS 复用 | 构模次数、RHS 更新、列并集大小、RMP 时间 | 模型复用是否因列池增长而退化 |
| 设计证书缓存开 / 关 | 重复设计率、命中、未闭合重求、内存 | 是否有足够重访来收回缓存代价 |
| 固定 / 自适应批量和平滑 | 原价接受率、正流参与度、证书间隔 | 更好的发现列是否改善相同时间下的界 |
| 有 / 无稳定化候选主问题 | master/试探/recourse 时间、UB/LB 轨迹 | 减少设计往返的收益是否超过额外求解 |
| 基础队列 / joint / design-face | 分离耗时、有效割数、认证 LB 进展 | 结构增强是否带来实际总体进展 |

UB 侧单独报告首次可行解、目标成本和同时间下的成本；LB 侧报告认证轨迹与 gap。切片到时、局部最优、受限列最优和整体达到 gap 是不同状态。跨 L 比较时，若要隔离基地数的效果，应对所有 L 同样关闭当前限定 L2/K2 的四个 ALNS 开关；不能让一个 L 获得额外算法预算而直接解释为结构收益。

### 第三优先级：由测量结果选择进一步开发

1. **若目录内存或预处理占主导**：优先考虑流式物理域、紧凑列表示和全域定价接口；必须保持完整域证书，不能用任意候选截断替代精确定价。
2. **若 master/根界占主导**：按每秒认证 LB 改善评估 joint/face 选择，使用候选筛选或任务聚类控制仍为 O(Q²) 的枚举；新的筛选只影响候选发现，已发割仍需完整状态证书。
3. **若 recourse 占主导**：评估动态列池、模型延续和数值恢复开销，再考虑安全列清理；清理列后必须重新定价恢复全域认证。
4. **若 UB 搜索占主导**：再考虑将 L2/K2 的 ALNS 推广到任意 L，以任务为基本操作，保留 incumbent 支持和原物理校验。
5. **若反复启动主问题树明确成为瓶颈**：才评估 single-tree/callback。它会改变回调上下文、证书时机和求解器生命周期，不适合作为服务器首轮实验前的顺手重构。

当前最有价值的工作是把“数学模型—冻结程序—有效运行—独立验证—统计比较”连成可重复的证据链。本轮提供了这条链的本地实现和 Windows 验收入口，后续算法优先级由服务器数据决定。
